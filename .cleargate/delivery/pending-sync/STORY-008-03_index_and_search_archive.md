# STORY-008-03: Index and search: `index.md` from `pages/` only, `search --archive`, archived facts in history searches
**Complexity:** L3 — cross-cutting in the search stack: a second page tree in the corpus and the cache (`src/search/engine.ts`), a new `--archive` option and tree-aware hit, entity and change building (`src/commands/search.ts`, `src/search/filters.ts`, `src/search/since.ts`, `src/search/aliases.ts`), and one counted line in `index.md` (`src/ingest/index-builder.ts`, `src/commands/index.ts`). Consumes K9 `paths.archiveDir` (STORY-008-01); builds on STORY-007-05's `page_tokens` in the same three search files, `src/search/engine.ts`, `src/commands/search.ts` and `src/search/filters.ts` (merge order 007-05 → 008-03; STORY-007-05 is a predecessor).

## 1. The Spec (The Contract)

### 1.1 User Story
As an AI coding agent answering questions from the wiki, I want `index.md` and ordinary searches to show only current pages, `search --archive` to reach archived pages when I need old detail, and history searches (`--since`, `--entity`) to include archived facts marked as archived, so that current answers stay small and "what changed since …" questions still find facts that a clean-up moved.

### 1.2 Detailed Requirements
- **R1 — `index.md` counts the archive (K11).** `buildIndex(pages, opts?: { archived?: number })` lists `pages/` entries exactly as today. When `archived > 0` it adds one line, after the `_Generated by … Do not edit._` line (or after `_No pages yet._` when `pages` is empty) and a blank line: `_<n> archived pages — search them with \`wikeeper search --archive\`._`, or for n = 1 `_1 archived page — search it with \`wikeeper search --archive\`._` (§1.4 Q3). `buildIndex(pages)` and `buildIndex(pages, { archived: 0 })` stay byte-identical to today (`test/ingest/log.red.node.test.ts:66`, `test/index-rebuild.red.node.test.ts:73`).
- **R2 — `writeIndex` counts `archive/` (K11).** `writeIndex(paths)` counts `listPageFiles(paths.archiveDir)` (`.md` files, dot segments skipped; a missing folder counts 0), passes the count to `buildIndex`, and returns it as `archived: number` (additive). Archive pages are counted, not parsed. Both callers get the line with no change of their own: `index rebuild` and `ingest finish` (`src/commands/ingest-finish.ts:102`, `:179`). `IndexRebuildResult.index` gains `archived: number`; the human message adds `, <n> archived` after `<n> pages` when n > 0: `rebuilt .wiki/index.md (12 pages, 3 archived) and .wiki/log.md (8 events)`.
- **R3 — Default search skips the archive.** Without `--archive`, a query, `--type` / `--where` / `--status` and `--mark` (without `--since` or `--entity`) return hits from `pages/` only, with the same results and scores as today: the default index holds `pages/` docs only.
- **R4 — `search --archive` (K11).** New option `--archive`, described `also search archived pages (archive/)`. With a query, filters or `--mark`, hits come from both trees, ranked together by one index over both trees' docs.
  - Every `SearchHit` has `archived: boolean`. An archived hit's `path` is relative to `archive/` (the same path as its `pages/` namesake), and its `file` is under the archive folder, e.g. `.wiki/archive/projects/atlas.md`. Its `page_tokens` (K7) is the archive page's: STORY-007-05's `SearchCorpus.pageTokens(path)` becomes `pageTokens(path, archived?: boolean)`, which reads the archive file's bytes when `archived` is true, and the single `page_tokens` pass in `executeSearch` passes `hit.archived`.
  - Human output: an archived hit's first line ends with ` (archived)`, e.g. `1. projects/atlas.md › Timeline (archived)`.
  - `--archive` with `--entity` or `--since` and nothing else changes nothing (R5, R6 always include the archive) and is accepted.
  - `--archive` with `--misses` → exit 2 `usage`, message `--misses cannot be combined with a query, --type, --where, --status, --mark, --entity or --archive`. `--archive` alone → the existing `give a query or a filter`.
  - `SearchRequest.archive?: boolean` (optional, like `noMiss`). It is not a filter: `data.filters`, `describeFilters` and the miss event format are unchanged, and a `--archive` search that finds nothing records a miss as today (§1.4 Q4).
- **R5 — `--entity` includes archived facts (K11).** Resolution tries `pages/` entities first, as today (`resolveEntity`).
  - The match's **archive counterpart** is the archive entity with the same `path` and `kind` and, for a section entity, the same `normalizeName(name)`.
  - `entity.facts` lists the match's facts (`archived: false`) and its counterpart's facts (`archived: true`), sorted as today (date descending, then line), live before archived on a tie.
  - When no `pages/` entity matches, `resolveEntity` runs over the archive entities. That match has `archived: true`, its `file` is under the archive folder, and every fact is archived (§1.4 Q2). `EntityMatch.archived: boolean` is additive, owned here.
  - Backlinks come from `pages/` as today; `also_matches` comes from the tree the match came from.
  - With `--since`, `changes.facts` covers the match and its counterpart, archived facts marked; `changes.pages` is unchanged.
  - Human output: an archived fact line ends with ` (archived)`; an archive-only match's first line ends with ` · archived`.
- **R6 — `--since` includes archived facts (K11).**
  - With no query and no filter, `changes.facts` covers every `pages/` entity and every archive entity.
  - With a query or filters, hits are kept as today, each judged by its own entity's facts; `changes.facts` covers the kept entities and their archive counterparts.
  - `changes.pages` lists the `pages/` changes recorded in ingest events, as today. `--mark` filters archived facts like live ones.
  - Human output: `- <date> · <status> · <text> (<path> › <section>, archived)`.
- **R7 — `FactView.archived: boolean` (K11)** on every fact view, in `entity.facts` and `changes.facts`.
- **R8 — Corpus and cache (K11).**
  - `loadSearchCorpus` reads both trees with `listPageFiles` (a missing `archive/` gives `[]`), each file read in parallel as `pages/` is today.
  - `SearchCorpus` gains `archivePages: Page[]`, `archiveEntities: Entity[]` and `archiveDocs: SearchDoc[]`; `SearchDoc` gains `archived: boolean`.
  - `corpus.index` stays over `pages/` docs. With `opts.archive: true`, `corpus.index` is one index over `pages/` docs and archive docs (archive ids continue after the `pages/` ids), built in memory for that run and not stored.
  - The cache stays one file, `.wiki/.cache/search.json`, with `SEARCH_CACHE_VERSION` 1 (§1.4 Q1). Its body gains `archive_files` (same shape as `files`, paths relative to `archive/`), `archive_pages` and `archive_docs`. `files` stays `pages/` only.
  - `isUsableCache` also requires `archive_files` to equal the archive keys, in order; a cache without `archive_files` is rebuilt. A change in either tree rebuilds the cache once.
- **R9 — Performance.** The default search adds only reading and hashing the archive files. `npm run test:perf` (500 pages, p95 under 500 ms with the cache off and warm; STORY-004-02, STORY-004-06) keeps passing, with those test files unchanged. No new budget is set for `--archive` runs.

### 1.4 Open Questions

- **Question (Q2, archive-only entity):** Should `--entity beta` find an entity whose page was moved whole to `archive/`?
- **Recommended:** Yes (R5): history lookups are what `--entity` is for, and EPIC-008 §2 says `--entity` includes archived facts. The match carries `archived: true` (`EntityMatch.archived`, additive to K11) so the agent says the entity is archived.

- **Question (Q3, index line wording):** K11 fixes `_<n> archived pages — search them with \`wikeeper search --archive\`._`, which reads badly for one page.
- **Recommended:** Singular for n = 1: `_1 archived page — search it with \`wikeeper search --archive\`._` (R1). STORY-008-06 quotes the line, if at all, with these two forms.
- **Human decision:** _approved as recommended (human, 2026-10-18, Gate 1; `plans/gate1-decisions.md`)_

- **Question (Q4, misses):** Should a `--archive` search that finds nothing record a miss, and should the miss record `--archive`?
- **Recommended:** Record it as today, without an `archive` key: a miss means the wiki did not answer, and leaving `encodeMissFilters` alone keeps `search --misses` grouping and its tests unchanged (`test/search/misses.test.ts:39`).

### 1.5 Risks

> Risks specific to this Story (cross-story risks belong in the milestone plan).

- **Risk:** An archive page keeps its `pages/` path, so its `Page.path` and entity keys (`projects/atlas.md`, `projects/atlas.md#L12`) equal its live namesake's. Any map that mixes the trees merges them: `pageByPath` and `entityByKey` (`src/commands/search.ts:167`, `:168`), the filter key set (`:155`) and the `byHit` map (`:232`).
- **Mitigation:** Keep separate `pages/` and archive maps and pick one by `doc.archived` or by the hit's tree. Unit tests use a name present in both trees in query, filter, `--mark`, `--entity` and `--since` mode.
- **Risk:** Every search now reads and hashes the archive, and the archive only grows (no line leaves it, K10).
- **Mitigation:** Parallel reads (FLASHCARD 2026-10-17 `#search #perf`); the default index excludes archive docs, so ranking cost is unchanged; the perf tests guard the archive-free path. If a large archive slows search, an archive section checked only when used is a follow-up, not this story.
- **Risk:** `src/search/engine.ts` and `src/commands/search.ts` are also edited by STORY-007-05 (`page_tokens`).
- **Mitigation:** 007-05 merges first; this story sets `page_tokens` for archived hits from the archive page and changes no 007-05 line beyond that.
- **Risk:** `--archive` builds an index over both trees on every run, as a cold search does.
- **Mitigation:** Accepted: `--archive` is the rare path, and a cold build of 500 pages is inside the existing 500 ms budget (`test/search/search-perf.red.node.test.ts:28`).

### 3.2 Technical Logic
- **Index (R1, R2).** `buildIndex` builds the archived line with `plural`-style wording (`page`/`pages`, `it`/`them`) and inserts it before the first `## <type>` section, or after `_No pages yet._`. `writeIndex` calls `listPageFiles(paths.archiveDir)` for the count and returns `{ file, pages, archived, changed, errors }`. `src/commands/index.ts:52` adds `, <n> archived` to the message; `IndexRebuildResult.index` gains `archived`.
- **Corpus (R8).** In `loadSearchCorpus` (`src/search/engine.ts:240`), list and read both trees in one `Promise.all`; hash each; keys `files` (pages) and `archive_files` (archive). `isUsableCache` (`:226`) checks both lists. On rebuild, parse archive pages with their archive-relative path, and build `archive_docs` with `buildDocs` plus `archived: true` (ids from 0 within the archive list). The cache body adds `archive_files`, `archive_pages`, `archive_docs`; `version` stays `SEARCH_CACHE_VERSION` (1). With `opts.archive`, renumber archive doc ids after the `pages/` docs and build the combined index with `newMiniSearch([...docs, ...archiveDocs])`; otherwise reuse the stored `pages/` index as today.
- **Hits (R3, R4).** `executeSearch` (`src/commands/search.ts:118`) passes `archive: req.archive === true` to `loadSearchCorpus`. Build one page map and one entity map per tree; `toHit` (`:169`) picks the tree from `doc.archived` and builds `file` from `paths.archiveDir` for archived docs. Filter mode (`:151`) and `markHits` (`src/search/filters.ts:147`) run over `pages/` entities, plus archive entities when `req.archive`; the key sets that filter ranked hits are tree-qualified. `entityHit` (`src/search/filters.ts:115`) and `markHits` take the tree so `file` and `archived` are right. Human rendering (`renderHuman`, `:295`) appends ` (archived)`.
- **Entity (R5).** After `resolveEntity(corpus.entities, …)`, find the counterpart in `corpus.archiveEntities`; if there is no live match, `resolveEntity(corpus.archiveEntities, …)`. `toEntityMatch` (`src/search/aliases.ts:81`) takes the tree and the counterpart, so `file`, `archived` and the merged, sorted `facts` are built in one place. Backlinks stay `buildBacklinks(corpus.pages)`.
- **Since (R6, R7).** `toFactView(fact, entity, page, archived = false)` (`src/search/since.ts:38`). `factsSince` runs once over `pages/` entities with `corpus.pages` and once over the chosen archive entities with `corpus.archivePages` (`archived: true`), then sorts the union with the existing order. Since-only mode passes every archive entity; query or filter mode passes the counterparts of the kept entities (and, under `--archive`, the kept archive entities themselves).
- **Usage (R4).** Register `--archive` after `--mark`; `missesUsage` (`:380`) also rejects `req.archive` and gains `or --archive` in its message.
- **Fixtures.** Write archive pages with `put()` under `.wiki/archive/` (the snapshot guard is not involved in search tests); count cache rebuilds with `onRebuild` (`SearchDeps & { onRebuild }`, FLASHCARD 2026-10-17 `#qa #red-test`). Red rows that assert an empty result first assert `json.ok` (FLASHCARD `#qa #red-test`). The `ingest finish` row of the first scenario runs a chat-excerpt ingest (`ingest start -` … `ingest finish`) that updates `pages/projects/atlas.md`, with the archive pages written before `ingest apply`.

## Why not simpler?

- **Smallest existing surface that could carry this:** `loadSearchCorpus` (`src/search/engine.ts:240`) with a second `listPageFiles` call, and `buildIndex` with one extra line.
- **Why isn't extension / parameterization / config sufficient?** It is extension. Pointing search at both folders with no tree marker is not enough: archive pages share paths and entity keys with their live namesakes, so hits, entity lookups and filters would merge the two pages; and default search must keep skipping the archive. The tree flag on docs, hits and facts, and the separate maps, are the smallest change that keeps both apart. No new module is added.
